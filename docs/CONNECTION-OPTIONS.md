# GameShare 信令与音视频连接配置

当前界面使用统一配置页（2026-11-07），流程为角色 → 信令连接 → 音视频连接。旧四种模式只保留在历史邀请与偏好的迁移逻辑中，不再作为界面入口。

## 1. 房主与加入者流程

**创建房间：**

1. 选择“创建房间”，填写可选昵称。
2. 选择信令方式并准备房间地址。
3. 独立选择音视频策略；需要指定 IP 时，选择自己电脑上的有效网卡地址。
4. 创建房间。Cloudflare 需等待临时网址就绪，再从顶部复制邀请。
5. 到“屏幕共享”选择屏幕或窗口；配置页切换不会停止共享。

**加入房间：**

1. 选择“加入房间”，粘贴房主的完整邀请。
2. 邀请一经识别，信令方式和音视频策略立即自动选择并锁定，避免加入者误改。
3. 如果媒体策略为“指定本机 IP（实验）”，加入者自行选择自己电脑的媒体 IP；不复制房主的本机 IP。
4. 点击“连接并加入”。加入者使用邀请里的服务地址，不启动自己的 Cloudflare 隧道。

没有邀请时可手动选择配置、填写房主地址和房间码。清空邀请后可解除邀请对配置的锁定。入房后全部网络配置锁定，离开房间后才能修改。

## 2. 信令连接方式

信令负责创建、加入、成员状态和媒体连接协商。

| 方式 | 房主需要填写 | 实际路径 |
| --- | --- | --- |
| IP 直连 | 选择本机可达 IPv4 / IPv6，包含局域网、UU 虚拟网卡和本机公网地址 | 朋友 → 对应 IP → 房主信令服务 |
| 自备外网地址 | 完整 http(s) 外网入口，包含实际映射端口 | 朋友 → 公网端口映射或穿透服务 → 房主信令服务 |
| Cloudflare 自动隧道 | 无需填写；软件内置 cloudflared 自动准备网址 | 朋友 → Cloudflare → 已建立隧道 → 房主信令服务 |

房主自己仍连接经过验证的本机信令地址。8080 被占用时只复用 /health 确认为 GameShare 的服务；无关服务占用则明确报错，不把错误端口当作房间入口。

自备穿透服务（花生壳、Tailscale Funnel 等）需自行配置；GameShare 不代为管理它们。信令映射需支持 HTTP / WebSocket。

### 穿透软件的字段怎么对应

- **穿透软件的内网服务 / 转发目标：** 本机 GameShare，例如 `http://192.168.x.x:8080`。先确认该目标的 `/health` 返回 `game-share-signaling`，HTTP 后端不要误选 HTTPS。
- **GameShare 的自备外网地址：** 穿透软件给出的“外网访问地址”，例如 `https://你的域名` 或 `http://公网IP:映射端口`。不填内网服务，也不要只复制“映射 IP”。外网端口不一定是 8080。
- **健康页：** 地址旁的链接用于手动检查；请朋友也访问，确认 `ok: true` 和 `service: game-share-signaling`。HTTP 健康不代表房间加入或媒体成功。

## 3. 音视频连接方式

音视频由 WebRTC 在成员之间建立连接，与信令入口独立。三种媒体策略都可与三种信令方式组合。

| 策略 | ICE 行为 | 是否手选媒体 IP |
| --- | --- | --- |
| 自动协商（推荐） | 本机候选＋STUN＋信令服务提供的可选 TURN | 否 |
| 局域网 / UU 自动连接 | 只使用本机候选，不配置 STUN / TURN | 否，自动选择可达路径，不锁定网卡 |
| 指定本机 IP（实验） | 不配置 STUN / TURN；限制候选并核对实际路径 | 是，房主和每个加入者分别选择 |

默认新用户为 Cloudflare 信令＋自动协商。已有本机偏好先迁移再恢复，单独保存信令和媒体策略；不保存媒体 IP，也不默认选第一张网卡。

### 选择媒体 IP

使用 UU 时双方各选自己的 UU IP；同一局域网可以选自己的真实网卡 IP。异地双方的 `192.168.x.x`、`10.x.x.x` 等私网地址通常不可达，信令穿透不会打通这些媒体地址。不要填写对方 IP 或穿透映射 IP。

指定 IP 策略保留当前实验约束：只公布所选 IP 的 host 候选，过滤发出 SDP 的其他候选，并核对实际本地地址。检测到地址不符、持续无法核对或所选 IP 消失时停止媒体，保留可用房间信令。**这不是原生 socket 绑定，核对前的流量仍可能经过其他地址，不能宣称严格无回退。** 正式底层绑定仍需另行验证，见 [媒体 IP 验证](MEDIA-IP-BINDING.md)。

STUN 辅助发现公网映射地址，不转发音视频；TURN 才中继媒体。自动协商由 ICE 选择路径，不承诺一定直连，也不是固定的“直连失败后才启动 TURN”流程。Cloudflare Tunnel 与 Cloudflare Realtime TURN 是独立能力，启用前者不会自动配置后者。

通过 UU 等虚拟网卡建立 WebRTC 端点连接时，虚拟网络底层可能自行中转，不能凭 P2P(host) 判断整条链路没有服务器中转。

### 常见组合

| 场景 | 信令 | 音视频 |
| --- | --- | --- |
| 同一局域网 / 双方已用 UU 组网 | IP 直连 | 局域网 / UU 自动连接 |
| 异地，希望软件自动准备入口 | Cloudflare 自动隧道 | 自动协商 |
| 已准备花生壳 / Funnel 网址 | 自备外网地址 | 自动协商 |
| 穿透连房间、明确用 UU IP 传画面 | Cloudflare 或自备外网地址 | 指定本机 IP（实验），各选自己的 UU IP |
| Cloudflare 进房、自动使用双方可达的虚拟网络 | Cloudflare 自动隧道 | 局域网 / UU 自动连接 |

## 4. 邀请与兼容

新邀请格式为 `GS3.<base64 JSON>`，载荷只包含：

- `server`：完整信令地址。
- `room`：房间码。
- `signaling`：`ip` / `external` / `cloudflare`。
- `mediaPolicy`：`internet-auto` / `local-auto` / `selected-ip-experimental`。

不携带房主媒体 IP、TURN 密钥或旧模式字段。新客户端接受全部九种组合，并在粘贴时独立应用两项设置。旧版支持 GS1 / GS2 的客户端无法按新配置读取 GS3，应提示升级；不附加可被旧客户端忽略媒体策略的降级邀请。

旧 GS1 的 lan / uu、public、cloudflare 分别迁移为对应信令与媒体配置；旧 GS2 的 mixed 迁移为指定 IP 实验策略，保留其 Cloudflare 或自备地址入口要求。缺少策略的更早邀请沿用当前配置，并明确提示用户与房主核对。未知策略、损坏邀请和声称严格绑定的旧 selected-ip 邀请仍被拒绝。

只有 IP 直连信令＋局域网 / UU 自动连接创建的房间开放唯一 IP 房间发现；其他组合手动加入需要房间码。邀请加入始终使用邀请中的房间码。

## 5. 状态与失败引导

- **没进房间：** 检查朋友能否访问房间入口 `/health`，核对映射、服务和防火墙；临时隧道重开后重发邀请。
- **已进房间、等待共享：** 还没有媒体共享或语音，不是媒体故障；到“屏幕共享”选择屏幕或窗口。
- **已共享、音视频失败：** 检查双方组网、媒体 IP 与防火墙。自动协商可使用已配置的 TURN，其他两种策略不使用 TURN。
- 房间状态与成员媒体状态分别展示；媒体详情展示本地 / 远端实际地址。修改网络配置需离房。
