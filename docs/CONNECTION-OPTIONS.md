# GameShare 信令与音视频连接方案

本文基于当前代码整理（2026-11-05），用树状图区分连接方案、界面入口和实际传输路径。

## 1. 总体分类

信令负责建房、加入房间、成员状态和连接协商；音视频链路负责传输画面、语音和共享声音。两者分别建立连接：能进入房间，不代表音视频已经连通。

```text
GameShare 连接
├── 信令连接：客户端如何访问信令服务器
│   ├── 直连信令服务器
│   │   ├── 本机地址：本机客户端访问本机服务
│   │   ├── 局域网地址：同一路由器、Wi-Fi 或热点
│   │   ├── 虚拟局域网地址：例如 UU 提供的虚拟 IP
│   │   └── 公网地址：可访问的公网 IPv4 / IPv6
│   └── Cloudflare Tunnel 转发
│       └── 通过临时公网地址访问本机信令服务
│
└── 音视频连接：客户端之间如何传输媒体
    ├── WebRTC 使用端点地址建立连接
    │   ├── 本地局域网连接
    │   ├── 公网 P2P 连接
    │   │   └── 可使用 STUN 辅助发现公网映射地址、尝试 NAT 穿透
    │   └── 虚拟局域网连接
    │       └── 使用虚拟网卡地址，由虚拟组网软件提供底层连通性
    └── WebRTC 使用 TURN 中继
        └── 媒体经过 TURN 服务器转发
```

“虚拟局域网”描述底层网络环境。对 GameShare 的 WebRTC 来说，它可以使用虚拟网卡地址连接；虚拟组网软件内部可能采用直连，也可能使用自己的中继，不能据此认定整条网络路径没有中转。

## 2. 信令服务的可选路径

```text
远端客户端访问信令服务
├── 方案 A：直连
│   ├── 局域网 IP → 信令服务器
│   ├── 虚拟局域网 IP → 信令服务器
│   └── 公网 IPv4 / IPv6 → 信令服务器
│       ├── IPv4：可能需要路由器端口映射
│       └── IPv6：需要双方网络支持，并允许相关入站连接
│
└── 方案 B：Cloudflare Tunnel 转发
    └── https://随机名称.trycloudflare.com
        └── Cloudflare 网络
            └── 已建立的隧道
                └── 房主电脑上的 cloudflared
                    └── 本机信令服务器
```

树中的箭头表示请求经过的路径，信令消息可以双向传输。`cloudflared` 由服务所在电脑主动向 Cloudflare 建立连接。

当前项目集成的是 Quick Tunnel，用于给本机信令服务器提供临时公网入口。房主本机客户端仍可直接连接本机信令服务，远端客户端通过隧道访问。同一个房间内，客户端访问同一信令服务的路径可以不同。

## 3. 音视频的可选路径

```text
客户端 A 与客户端 B 的音视频链路
├── 本地局域网
│   └── A ↔ 本地网络 ↔ B
├── 公网 P2P
│   ├── A ↔ 互联网 ↔ B
│   └── STUN 辅助获取可用地址，不承担音视频中继
├── 虚拟局域网
│   ├── A 的虚拟网卡 ↔ 虚拟网络 ↔ B 的虚拟网卡
│   ├── 当前界面在 IP 连接入口提供 UU 使用说明
│   └── 需要双方先在外部组网软件中建立可达的网络
└── TURN 中继
    ├── A ↔ TURN 服务器 ↔ B（示意，实际可能使用两端的中继候选）
    ├── 当前接入：Cloudflare Realtime TURN
    └── 需要信令服务配置 TURN，并向客户端提供有效临时凭证
```

Tailscale、ZeroTier 等也属于虚拟组网工具，但当前界面没有它们的专用入口，本文不将它们列为已经验证可用的集成方案。

Cloudflare Tunnel 和 Cloudflare Realtime TURN 是两项独立能力：当前项目的 Tunnel 转发信令，TURN 转发音视频。启用隧道不会自动获得音视频中继能力。

## 4. 四种界面入口与媒体策略

| 入口 | 信令入口 | 媒体策略 | 当前状态 |
|---|---|---|---|
| IP 连接（`lan`） | 局域网或虚拟局域网 IP | 本机候选，不配置 STUN / TURN | 可用 |
| 公网连接（`public`） | 可访问的公网 IPv4 / IPv6 | 本机候选、STUN、可选 TURN | 可用 |
| 异地便捷连接（`cloudflare`） | Cloudflare Tunnel 临时地址 | 本机候选、STUN、可选 TURN | 可用 |
| 混合模式（`mixed`，实验） | 自选 IP 或 Cloudflare Tunnel | 各自指定本机媒体 IP；候选限制与实际路径检查 | 开放测试，严格底层绑定未验证 |

UU 与本地局域网统一为 IP 连接，不再二次选择网络来源。使用 UU 时选择 UU 显示的虚拟 IP；本地网络选择局域网 IP。历史 `uu` 偏好自动迁移为 `lan`。IP 模式仍会收集所有本机候选，**不代表绑定了信令地址对应的网卡**。

前三种入口是快捷配置。公网和异地入口由 ICE 选择媒体路径，不强制 P2P 或 TURN，也不采用固定的“直连失败后再启用 TURN”流程。

### 房主与加入者引导

- IP 房主：确认网络互通 → 选择朋友可达的 IP → 创建房间 → 复制邀请。只有一个候选地址时自动选择；多个地址时必须明确选择。
- 公网房主：确认端口与公网地址可达 → 选择或填写对外地址 → 创建房间 → 复制邀请。格式正确不等于外网可达。
- 异地房主：创建房间 → 等待临时地址 → 就绪后复制邀请；失败可重试，未就绪时不能复制。
- 加入者优先粘贴邀请；IP / 公网入口保留手动地址和房间码。IP 模式仍支持服务器只有一个可按 IP 加入的房间时省略房间码。
- 加入后锁定网络配置，离开房间后才能切换。房间信令状态与成员的媒体状态分别展示；媒体实际路径详情显示本地、远端地址。

### 邀请兼容

新普通邀请沿用 `GS1`，增加可选 `mode` 与 `mediaPolicy`（`local-auto` / `internet-auto`）。加入时以邀请配置为准；旧邀请保留当前模式，并记录未携带模式的提示。未知或矛盾策略明确拒绝。

混合实验邀请使用 `GS2`，携带 `mode: mixed`、`mediaPolicy: selected-ip-experimental` 和 `signaling: ip | cloudflare`，不携带房主的媒体 IP。加入者粘贴后自动进入混合配置，邀请保持在输入框，必须选择自己电脑上的媒体 IP 才能继续。加入者使用房主提供的隧道地址，不启动自己的隧道。

混合邀请不附带 GS1、旧文本地址或裸地址房间码兜底，避免旧客户端忽略媒体策略后按普通模式加入。当前客户端仍拒绝声称严格绑定的 `selected-ip` 策略。已发布旧客户端无法补加升级提示，只能通过版本格式避免自动识别；双方应使用此次测试版本。

### 混合实验模式

模式可直接进入，无需修改开关或配置文件。选择角色、IP / Cloudflare 信令方式，再选择本机媒体 IP。网卡列表包含非回环的有效 IPv4 / IPv6，保留虚拟网卡、显示名称，不默认替用户选择。IP 信令房主可选择本机地址或手填公网映射地址；Cloudflare 信令房主等待隧道就绪后复制邀请。加入者也可手动填写信令 URL 和房间码。

实验媒体层不配置 STUN / TURN，仅公布所选 IP 的 host 候选，并过滤发出 SDP 中的其他候选；每 500ms 核对实际连接路径，发现不同地址或无法确认地址时关闭该成员媒体连接并明确报错。每 2 秒刷新本机地址，所选 IP 消失时停止本机全部媒体连接，保留可用房间信令。修改配置需先离开房间。

**这是实验性路径限制与事后核对，不是原生 socket 绑定。连接检查或媒体在核对前仍可能经过其他地址，不能宣称严格无回退。** 不因此禁用入口，用户可实际测试连通性及地址匹配情况；严格绑定作为后续正式能力另行验证，见 [媒体 IP 绑定验证](MEDIA-IP-BINDING.md)。

## 5. 使用与排查时的判断

```text
连接结果
├── 信令未连通
│   └── 检查地址、服务端口、防火墙，或 Cloudflare 隧道状态
├── 已进入房间，但音视频未连通
│   ├── 局域网 / UU：检查网络互通、设备隔离、虚拟组网和防火墙
│   └── 公网 / Cloudflare：检查 P2P 可达性及 TURN 配置、凭证和可达性
└── 音视频已连通
    └── 查看实际选中的 ICE 候选对，判断是否使用 TURN
```

以上是连接层排查入口。画面、声音异常还可能来自采集、权限、轨道或播放环节。多人房间中，每对客户端的媒体路径可能不同，不能用一个连接入口名称代表所有人的实际传输路径。
